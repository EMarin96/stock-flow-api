# 003 · Stock movements — Plan

## Approach

Vertical Slices under `src/Application/StockMovements/`: `CreateStockMovement/`, `GetStockMovements/`, `GetLocationStock/`. Same CQRS split as 001/002 — the create command goes through EF Core, the two queries go through Dapper. `StockMovement` references existing `Product` and `Location` aggregates by ID only (no navigation properties), reusing `ProductErrors.NotFound`/`LocationErrors.NotFound` from their respective `Shared/` folders instead of duplicating "not found" errors for a third time.

Current stock is **materialized**, not computed on read: a new `StockLevel` entity (one row per product+location) is mutated atomically, in the same `SaveChangesAsync()` call as the `StockMovement` insert. This reverses the "current stock is calculated, not stored" principle previously documented in `constitution/tech-stack.md` — see that file's updated wording. It was chosen over compute-on-read because: (a) it makes `GET /api/locations/{locationId}/products` a simple indexed read instead of an aggregation over the full movement history, and (b) it lets the negative-stock guard be a single-row check backed by a real DB constraint, closing the race-condition risk that compute-on-read could only leave as an accepted risk.

## Implementation

1. `src/Domain/StockMovements/MovementType.cs` — enum `In`/`Out`/`Transfer`/`Adjustment`.
2. `src/Domain/StockMovements/MovementDirection.cs` — enum `Increase`/`Decrease`, used only when `Type == Adjustment`.
3. `src/Domain/StockMovements/StockMovement.cs : Entity` (not `AuditableEntity` — no `UpdatedAt`/`UpdatedBy`, movements are never edited). Fields: `ProductId`, `Type`, `Quantity` (int), `SourceLocationId` (`Guid?`), `DestinationLocationId` (`Guid?`), `Direction` (`MovementDirection?`), `CreatedAt`, `CreatedBy`. `Create(...)` guard clauses (throwing `DomainValidationException`, same pattern as `Sku`/`Money`/`Address`): `Quantity > 0`; per-`Type` location-field requirements (`In`→destination only, `Out`→source only, `Transfer`→both, `Adjustment`→destination only); `Direction` required iff `Type == Adjustment`, must be `null` otherwise.
4. **New: `src/Domain/StockMovements/StockLevel.cs : Entity`** — `ProductId`, `LocationId`, `Quantity` (int, ≥ 0). Static `Create(productId, locationId)` starts at `Quantity = 0`. Behavior methods `Increase(int amount)` / `Decrease(int amount)` — `Decrease` guard-clause throws `DomainValidationException` if it would go negative (defense-in-depth; unreachable in normal flow since the Application handler and the DB `CHECK` constraint both catch it first — see Decisions).
5. `src/Application/StockMovements/Shared/`:
   - `IStockMovementWriteRepository.cs` — `Add(StockMovement)`.
   - `IStockLevelWriteRepository.cs` — `GetOrCreateAsync(productId, locationId, ct)` (tracked, mutated in place by the Create handler within the same `SaveChangesAsync()` as the movement insert).
   - `IStockMovementReadRepository.cs` — `GetPagedAsync(page, pageSize, productId?, locationId?, type?, ct)`.
   - `IStockLevelReadRepository.cs` — `GetPagedByLocationAsync(locationId, productNameFilter?, page, pageSize, ct)` (Dapper, joins `Products` for name/SKU).
   - `StockMovementDto.cs`, `StockMovementMappingExtensions.cs`, `LocationStockDto.cs`.
   - `StockMovementErrors.cs` — `InsufficientStock`, `InvalidLocationForType`, `DirectionRequired`/`DirectionNotAllowed`, `CrossCountryTransfer`, `ValidationFailed`. (`ProductNotFound`/`LocationNotFound` reuse `ProductErrors.NotFound`/`LocationErrors.NotFound` directly — no new error needed.)
6. `src/Application/StockMovements/CreateStockMovement/` — `CreateStockMovementCommand` (`ProductId`, `Type`, `Quantity`, `SourceLocationId?`, `DestinationLocationId?`, `Direction?`) + `CreateStockMovementValidator` (quantity > 0, enums valid, conditional location/direction presence per `Type` via FluentValidation `When(...)`) + `CreateStockMovementHandler`:
   - Load `Product` (write repo) — 404 via `ProductErrors.NotFound` if missing/soft-deleted.
   - Load referenced `Location`(s) (write repo) — 404 via `LocationErrors.NotFound` if missing/soft-deleted.
   - If `Transfer`: compare `SourceLocation.Address.Country` vs `DestinationLocation.Address.Country` — reject via `StockMovementErrors.CrossCountryTransfer` if different.
   - For each affected location, `stockLevelRepository.GetOrCreateAsync(...)`, then call `.Increase(...)`/`.Decrease(...)` per type/direction — catch the Domain guard exception and translate it to `StockMovementErrors.InsufficientStock` (an expected business outcome here, not a truly unexpected error, so it's caught and converted rather than left to bubble as a 500).
   - `StockMovement.Create(...)`, `writeRepository.Add(...)`, single `unitOfWork.SaveChangesAsync()` persists the movement and every mutated `StockLevel` row atomically.
7. `src/Application/StockMovements/GetStockMovements/` — `GetStockMovementsQuery` (`Page`, `PageSize`, `ProductId?`, `LocationId?`, `Type?`) + `GetStockMovementsValidator` (page/pageSize bounds, same as `GetProducts`/`GetLocations`) + `GetStockMovementsHandler` (Dapper, `LocationId` filter matches either `SourceLocationId` or `DestinationLocationId`).
8. **New: `src/Application/StockMovements/GetLocationStock/`** — `GetLocationStockQuery` (`LocationId`, `ProductNameFilter?`, `Page`, `PageSize`) + `GetLocationStockValidator` (page/pageSize bounds; `LocationId` required) + `GetLocationStockHandler` (Dapper; 404 via `LocationErrors.NotFound` if the location doesn't exist; returns every `StockLevel` row for that location — including `Quantity = 0` — joined to `Products` for `Sku`/`Name`, optionally filtered `WHERE ProductName ILIKE '%' || @filter || '%'`, paginated). Response per row: `{ ProductId, ProductSku, ProductName, Quantity }`.
9. `src/Infrastructure/Persistence/Configurations/StockMovementConfiguration.cs` — table `StockMovements`; FK to `Products` (`ProductId`, restrict delete); FKs to `Locations` for `SourceLocationId`/`DestinationLocationId` (both nullable, restrict delete); `Type`/`Direction` via `HasConversion<string>()`; no soft-delete flag/global filter (nothing ever deletes a movement).
10. **New: `src/Infrastructure/Persistence/Configurations/StockLevelConfiguration.cs`** — table `StockLevels`; composite unique index on (`ProductId`, `LocationId`); FKs to `Products`/`Locations` (restrict delete); DB-level `CHECK ("Quantity" >= 0)` constraint (via `.ToTable(t => t.HasCheckConstraint(...))`) as the final safety net against races, same role as the SKU unique index in 001.
11. `src/Infrastructure/Persistence/Repositories/StockMovements/StockMovementWriteRepository.cs` (`Add`) and `StockLevelWriteRepository.cs` (`GetOrCreateAsync` — EF `FirstOrDefaultAsync`, or tracked `Add` of a fresh `StockLevel.Create(...)` if no row exists yet). Repositories live under `Repositories/{Feature}/`, one Read (Dapper) file and one Write (EF) file per feature — matching the same split already used for `Products`/`Locations`.
12. `IUnitOfWork`'s existing DB-error-translation (already handles unique-constraint violations for SKU/Location code) gets a second case: a Postgres check-constraint violation on `StockLevels` → translated to `StockMovementErrors.InsufficientStock`, so a race that slips past the Application-layer guard still surfaces as the same clean business error instead of an unhandled 500.
13. Dapper queries: `GetPagedAsync` (movements) and `GetPagedByLocationAsync` (location stock, joined to `Products`).
14. Migration: `AddStockMovementsAndStockLevelsTables`.
15. `src/Api/Endpoints/StockMovementEndpoints.cs` — `POST /api/stock-movements` (create), `GET /api/stock-movements` (list, query params `page`/`pageSize`/`productId`/`locationId`/`type`), wired via `app.MapStockMovementEndpoints()`.
16. `src/Api/Endpoints/LocationEndpoints.cs` — **new**: `GET /api/locations/{locationId}/products` (query params `productName?`, `page`, `pageSize`) → `GetLocationStockQuery`. Lives here (not in `StockMovementEndpoints.cs`) because it's nested under the `/api/locations` resource — a location's product/stock listing, not a stock-movements query.
17. Swagger annotations/response types for every new endpoint, per convention.
18. Tests: Domain (`StockMovement.Create` and `StockLevel.Increase`/`Decrease` guard clauses), Application (validators + handlers, including the insufficient-stock and cross-country-transfer rejections, using in-memory test-double repositories like `InMemoryLocationWriteRepository`), Api integration tests (Testcontainers Postgres, covering every acceptance criterion in `spec.md`, including a concurrency test asserting the DB `CHECK` constraint rejects a stock level going negative).

## Decisions

- **`StockMovement : Entity`, not `AuditableEntity`** — only `CreatedAt`/`CreatedBy` are meaningful for an append-only record; adding unused `UpdatedAt`/`UpdatedBy` would misrepresent that the record can change.
- **Stock is materialized as `StockLevel`, not computed on read** — reverses the principle previously stated in `constitution/tech-stack.md`; that doc is updated alongside this plan. Chosen because it turns the negative-stock guard into a single-row, DB-constrained check instead of an on-the-fly aggregation, and makes the location-stock listing a plain indexed read.
- **Negative-stock guard enforced twice, deliberately** — once in `CreateStockMovementHandler` (clean business error on the expected path) and once as a DB `CHECK` constraint on `StockLevels` (final backstop against races, translated by `IUnitOfWork` into the same error). This mirrors the existing SKU-uniqueness pattern from 001 (pre-check + DB unique index) — not new duplication, the same established pattern applied to a new invariant.
- **Cross-country `TRANSFER` check reads both `Location.Address.Country` values** — enforced in the Application handler (needs to load two `Location` records), not in a Domain guard clause, matching why `AddressReferenceDataValidator` lives in Application for feature 002.
- **`LocationId` filter on `GetStockMovements` matches either `SourceLocationId` or `DestinationLocationId`** — a user looking at one warehouse wants to see everything that moved through it.
- **`GET /api/locations/{locationId}/products` replaces the earlier single product+location lookup idea** — that endpoint would have needed required query params to identify one specific resource, which doesn't fit REST collection semantics; this is a real collection (every product with a stock record at that location), naturally supporting pagination and a name filter.
- **Reusing `ProductErrors.NotFound`/`LocationErrors.NotFound`** instead of defining `StockMovements.ProductNotFound`/`StockMovements.LocationNotFound` — same error code/message either way; extends the shared-error-factory convention across features, not just within one.
- **`StockMovement` and `StockLevel` are two separate entities, not one DDD Aggregate** — `StockLevel` isn't contained by a `StockMovement` instance (it outlives and is shared across many movements, and is loaded independently by `GetOrCreateAsync`, not navigated from a movement); it doesn't fit strict aggregate composition. This is instead the common **ledger + running balance** pattern: two entities coordinated atomically by `CreateStockMovementHandler` + `IUnitOfWork` within one transaction, already anticipated by `tech-stack.md`'s `IUnitOfWork` bullet ("atomic operations across multiple entities, needed later for `StockMovement` `TRANSFER`"). Considered and rejected: making `Location` an aggregate root owning a `StockLevels` collection — more textbook-DDD, but it would mix feature 002's (`Location` profile) and 003's (inventory) responsibilities, and this codebase already uses per-entity repositories rather than per-aggregate ones.

## Risks

- **`StockLevel` row creation race** — `GetOrCreateAsync` for a product+location that has no row yet could race with a concurrent first movement for the same pair, both trying to insert. Mitigated by the composite unique index on (`ProductId`, `LocationId`) — the loser's insert fails the constraint and is translated by `IUnitOfWork` into a retryable/clean error, same shape as every other unique-constraint race in this codebase.
- **`StockLevel` and `Product`/`Location` soft-delete interaction** — a `StockLevel` row references a product/location by FK with restrict-delete, but those use soft delete, not hard delete, so this is a non-issue in practice; noted here so it isn't silently assumed away if hard deletes are ever introduced later.
