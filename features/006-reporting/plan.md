# 006 · Reporting / read-only views — Plan

## Approach

A new Vertical Slice, `src/Application/Reporting/`, with one query/handler pair per report (`GetStockOverview/`, `GetMovementActivity/`), mirroring the existing `StockMovements`/`Locations` slices. Both are pure reads over data already written by Products/Locations/StockMovements — no new entity, no new write path, no new EF Core migration. Dapper (read side of CQRS) does the aggregation in SQL rather than pulling raw rows and aggregating in the Application layer, consistent with how every other list endpoint already delegates paging/filtering to the read repository.

## Implementation

1. `src/Application/Reporting/Shared/StockOverviewDto.cs` — `sealed record StockOverviewDto(Guid ProductId, string ProductSku, string ProductName, int MinimumStockThreshold, int TotalQuantity, bool IsLowStock)`.
2. `src/Application/Reporting/Shared/MovementActivityDto.cs` — `sealed record MovementActivityDto(Guid ProductId, string ProductSku, string ProductName, MovementType Type, int MovementCount, int TotalQuantity)`.
3. `src/Application/Reporting/Shared/IReportingReadRepository.cs` — one interface, two methods (`GetStockOverviewAsync`, `GetMovementActivityAsync`), same "one repository per feature, multiple methods" convention as `ILocationReadRepository`.
4. `src/Application/Reporting/Shared/ReportingErrors.cs` — `ValidationFailed(validationResult)`, same shape as every other feature's `Errors` class.
5. `src/Application/Reporting/GetStockOverview/` — `GetStockOverviewQuery(int Page, int PageSize, bool? LowStockOnly)` + Handler (validate → delegate to repository) + Validator (`Page`/`PageSize` bounds, same as `GetStockMovementsValidator`).
6. `src/Application/Reporting/GetMovementActivity/` — `GetMovementActivityQuery(DateTime? From, DateTime? To, Guid? ProductId, Guid? LocationId, int Page, int PageSize)` + Handler + Validator (`Page`/`PageSize` bounds; `From <= To` when both are supplied).
7. `src/Infrastructure/Persistence/Repositories/Reporting/ReportingReadRepository.cs` — Dapper implementation:
   - Stock overview: `Products` (filtered `IsDeleted = false`) `LEFT JOIN StockLevels` grouped by product, `COALESCE(SUM(...), 0)` for products with no `StockLevel` rows at all (mirrors `GetLocationStockRepository`'s `COALESCE` pattern), `IsLowStock` computed as `TotalQuantity <= MinimumStockThreshold` (at-or-below, the conventional "needs reordering" point — see Decisions), optional `WHERE`-after-aggregation filter for `lowStockOnly`.
   - Movement activity: `StockMovements JOIN Products` (movements reference products by id only, per `StockMovement`'s existing plan.md decision; **not** filtered by `Products.IsDeleted`, since this is a historical/audit view — see Decisions), grouped by `(ProductId, Type)`, filtered by `CreatedAt` range / `ProductId` / `LocationId` (matching source or destination, identical condition to `StockMovementReadRepository.GetPagedAsync`).
8. `src/Api/Endpoints/ReportingEndpoints.cs` — `MapReportingEndpoints`, group `/api/reports` tagged `"Reporting"`:
   - `GET /stock-overview` (`page`, `pageSize`, `lowStockOnly` query params) → `Produces<PagedResult<StockOverviewDto>>()`, `ProducesValidationProblem()`.
   - `GET /movement-activity` (`from`, `to`, `productId`, `locationId`, `page`, `pageSize` query params) → `Produces<PagedResult<MovementActivityDto>>()`, `ProducesValidationProblem()`.
   Neither calls `.RequireAuthorization(...)` — both fall through to the global fallback policy (`RequireAuthenticatedUser()`, any role), identical to every other GET endpoint (`GetLocations`, `GetStockMovements`, `GetLocationStock`, the 005 Country endpoints).
9. `Program.cs` — add `app.MapReportingEndpoints();` next to the other `Map*Endpoints()` calls.
10. `src/Infrastructure/DependencyInjection.cs` — `services.AddScoped<IReportingReadRepository, ReportingReadRepository>();`.
11. Tests:
    - `tests/StockFlow.Tests/TestDoubles/InMemoryReportingReadRepository.cs` — seeded with pre-aggregated `StockOverviewDto` rows (mirrors how `InMemoryStockLevelReadRepository` seeds pre-aggregated `LocationStockDto` rows rather than reconstructing from `Product`+`StockLevel`) for stock overview, and raw per-movement seed rows (`ProductId`, `ProductSku`, `ProductName`, `Type`, `Quantity`, `SourceLocationId`, `DestinationLocationId`, `CreatedAt`) grouped in-memory for movement activity (mirrors `InMemoryStockMovementReadRepository`'s filter-then-paginate style, extended with the `GROUP BY (ProductId, Type)` step the real SQL does).
    - `tests/StockFlow.Tests/Application/Reporting/GetStockOverview/GetStockOverviewHandlerTests.cs` — returns every seeded row; `lowStockOnly=true` filters correctly; invalid page/pageSize returns a validation error.
    - `tests/StockFlow.Tests/Application/Reporting/GetMovementActivity/GetMovementActivityHandlerTests.cs` — groups correctly by product+type; filters by `from`/`to`/`productId`/`locationId` (location matching either source or destination); `from > to` returns a validation error.
    - `tests/StockFlow.Tests/Api/Reporting/ReportingEndpointsTests.cs` — integration tests seeding real `Product`/`Location`/`StockMovement` rows through the existing endpoints (`Create*`, `POST /api/stock-movements`) then asserting both report endpoints' shape: total-quantity aggregation across locations, `IsLowStock` flag, `lowStockOnly` filtering, movement-activity grouping/count/total, date-range/product/location filtering, 401 with no token, 200 with a ReadOnly-role token (proving no write-role restriction was accidentally applied), 400 for `from > to` and for an out-of-range `pageSize`.

## Decisions

- **"Low stock" is `TotalQuantity <= MinimumStockThreshold` (at-or-below), not strictly `<`** — a product sitting exactly at its reorder point is conventionally already flagged as needing attention in inventory systems; this is a **local, revisitable** choice for the reporting feature only. The future Low-stock alerts backlog feature can choose its own comparison independently — it is not required to reuse this exact semantics, since alerting (push) and reporting (pull) are different concerns with potentially different thresholds/debouncing needs.
- **Movement activity is grouped by `(ProductId, Type)` only, never by location** — a `TRANSFER` movement has both a source and a destination location; grouping by a single location column would either double-count that movement (once per location) or silently pick one arbitrarily. `locationId` stays available as a filter (matching source or destination, identical to the existing `GetStockMovements` query) without being a `GROUP BY` key, avoiding the ambiguity entirely rather than picking an arbitrary tie-break.
- **Movement activity does not filter out movements referencing a since-soft-deleted product** — unlike `stock-overview` (a snapshot of the *current, active* catalog, where a deleted product no longer meaningfully has a "current total"), movement activity is inherently a historical/audit view; excluding a deleted product's past movements would silently erase real history. `StockMovement` already stores `ProductId` only (no navigation property, no cascade), consistent with its existing append-only design.
- **A single `IReportingReadRepository` with two methods, not two separate interfaces** — both queries are read-only aggregations that exist purely to serve this feature's two endpoints; splitting them into two interfaces (and two Infrastructure classes) would add ceremony with no reuse benefit, whereas `ILocationReadRepository` already establishes the "one repository, several methods, one feature" precedent in this codebase.
- **No FluentValidation rule limits how wide a `from`/`to` range can be** — the existing `GetStockMovements` query has no date-range concept at all today, and a wide range is just a bigger (still paginated) result set, not a correctness problem; revisit only if a real performance issue shows up.
- **Reused the exact `LocationId`-matches-source-or-destination semantics from `StockMovementReadRepository`** rather than inventing a new one, so a caller who already understands that filter on the movements list doesn't need to learn a second convention for the same concept on this report.

## Risks

- **`IsLowStock` semantics (`<=` vs `<`) diverging from whatever the future Low-stock alerts feature chooses** — explicitly called out as an independent, revisitable decision (see Decisions) rather than something this feature locks in for the whole system.
- **Dapper's `GROUP BY` + pagination requires the count query to re-run the same grouping** (via a `SELECT COUNT(*) FROM (... GROUP BY ...) sub`, not a plain `COUNT(*)`) — mitigated by an integration test asserting `TotalCount` matches the actual number of distinct `(ProductId, Type)` groups, not the raw movement row count.
- **A product with zero `StockMovement` rows anywhere still appearing correctly in `stock-overview` but never in `movement-activity`** — expected and intentional (movement-activity only has something to group when a movement exists), but worth a regression test so a future change doesn't "fix" this into an unwanted zero-row entry.
